# Qwen3.8-27B in Eke Hive

> **Status (2026-10-09):** the CPU-only daemon `hived_q27_cpu` is validated against the reference (numbers below) and serves chat,
> thinking, tool-call prompts, images and MTP speculation through the API server. The GPU daemon `hived_q27` (sm_120a, with layer
> placement under a VRAM cap) **builds but has not run on a GPU yet** — nothing on this page about the GPU path is a measurement.

Eke Hive's fourth model family is **Qwen3.8-27B** (config.json `model_type` `qwen3_5`, architecture `Qwen3_5ForConditionalGeneration`),
from the official compressed-tensors checkpoint `Qwen3.8-27B-NVFP4` (~22 GB). The daemon is the same source (`engine/src/hived.cpp`) built
as `hived_q27` (GPU) and `hived_q27_cpu` (CPU only); the launcher picks the family from `config.json`.

## Model and checkpoint

| Part | Shape | Format in the checkpoint |
|---|---|---|
| 48 Gated DeltaNet layers (every layer but 3, 7, …, 63) | in_proj_qkv 10240 · in_proj_z 6144 · out_proj; 16 key / 48 value heads × 128; conv 4 | qkv / z / out **FP8 e4m3, one bf16 scale per row**; in_proj_a / in_proj_b, conv, A_log, dt_bias, norm BF16 |
| 16 full-attention layers (3, 7, …, 63) | 24 query heads (with an output gate) / 4 KV heads × 256, partial M-RoPE (64 dims) | q / k / v / o **FP8 per row** |
| dense MLP, every layer | 5120 → 17408 → 5120, SwiGLU | layers 0-55 **NVFP4** (e2m1 + e4m3 per 16 + fp32 global scale g, W = e2m1 · s / g); layers 56-63 **FP8 per row** |
| lm_head (untied) | 248320 × 5120 | **FP8 per row** |
| token embedding | 248320 × 5120 | BF16 |
| MTP (`model_mtp.safetensors`) | fc [5120, 10240] + one full-attention decoder layer + norm | BF16 (850 MB) |
| vision encoder | 27 blocks × 1152, patch 16, temporal 2, 2×2 merge → 5120, no deepstack | BF16 |

Not in 27B, compared with Flash-Next (`docs/qwen.md`): MoE, hyper-connections, PLE, the QSA sparse-attention indexer (verified from
config.json and the tensor list). Shared with Flash-Next: the Gated DeltaNet recurrence, the gated full attention with (1 + w) q/k norms,
interleaved M-RoPE (θ 1e7, sections 11/11/10), the MTP entry rules, the vision encoder structure, the chat template and image
preprocessing. Two details differ in the shared parts: the DeltaNet output norm is gated by **SiLU(z)** (config `output_gate_type` swish;
Flash-Next: sigmoid) and the residual stream is a plain pre-norm residual.

The math contract (every bf16 rounding point) is written in `engine/include/hive/q27/q27_model.h`; `oracle/q27_oracle.py` is its
executable form (this project's own PyTorch code, written from the math). Contract choices: activations are **not** quantized (W8A16 /
W4A16; the checkpoint's dynamic activation-quantization metadata and its FP8 KV scales are not used — KV caches are bf16); cos / sin of
the rotary are fp32 (transformers uses the activation dtype); a linear is fp32 accumulation over the dequantized weight, rounded once.

## CPU only: `hived_q27_cpu`

```bash
HIVE_GPU=none HIVE_CKPT=/models/Qwen3.8-27B-NVFP4 scripts/hive-start.sh   # (needs the launcher mapping listed under "Integration")
```

Every weight is copied once into NUMA-split host memory in its checkpoint format (18.6 GiB) and computed by the shared CPU backend
(`hive/cpu/cpu_backend.h`: FP8 per-row and NVFP4 GEMV / GEMM kernels, bf16 KV attention). Code: `engine/include/hive/q27/q27_cpu.h`,
`engine/src/q27/cpu/` — adapted from the Flash-Next CPU engine (the DeltaNet recurrence, attention row prep, verify snapshots, MTP
bookkeeping and the vision encoder are the same code with 27B's shapes).

Switches: `HIVE_Q27_MTP_K` (draft length, default 3; 0 = no MTP), `HIVE_Q27_CPU_CHUNK` (prefill rows per forward, default 2048),
`HIVE_Q27_MTP_INPUT=post` (A/B only, see below), `HIVE_CPU_POOL_THREADS` (backend workers, default = physical cores).

## GPU: `hived_q27`

**Precision policy (2026-10-10):** the default is lossless — numerically the official NVFP4 checkpoint with bf16 activations
(bit-identical kernels such as the swapped GEMV, DFlash2 / MTP with exact verification, scheduling, CUDA graphs, fusion and overlap are
allowed). W8A8 / W4A4 prefill (`HIVE_Q27_PREFILL_QUANT`) and NVFP4 decode copies (`HIVE_Q27_W4`) stay opt-in and are reported only in a
separate column, never as the headline. Low-bit speed is a separate track.

`engine/include/hive/q27/q27_engine.h`, `engine/src/q27/q27_engine.cpp`, `q27_kernels.cu`, `q27_lowp.cu`, `q27_dflash.cu`. Validated on the
RTX PRO 6000 (96 GB, 600 W) against the oracle (`q27_check` + `tools/compare_q27.py o1 <out>`: top-1 9/9, mean top-20 overlap 0.994 for the
lossless paths); speculative decode == greedy for single and batched verifies.

**Weights and decode.** Weights stay in their checkpoint format (FP8 per row, NVFP4, BF16). Decode / verify rows (≤ 32) use the swapped
tensor-core GEMV (`HIVE_Q27_SW=1`: weights as the mma A operand, tokens as B, cvt-exact FP8/FP4 → bf16, fp32 accumulation, one code path
for every row count → decode, verify and batch rows agree bit for bit; ~1.5 TB/s on the large matrices). Whole decode / verify steps run
as CUDA graphs (captured at start-up by the warm-up). Decode attention splits the keys (flash decoding, all 6 query heads of a KV head per
block): 6K-context step 42.5 → 15.3 ms. The GDN recurrence keeps 32 rows of a state column per lane (8 columns × 4 quarters per warp).

**Prefill.** Lossless default: one matrix at a time dequantized to exact bf16 + cuBLAS (fp32 out, scale epilogue). Attention: FA2-style
tensor-core kernel (`HIVE_Q27_FA2`, 4 warps × 16 query rows, cp.async double buffer, swizzled ldmatrix). GDN: chunked delta rule for
one-sequence prefills ≥ 128 rows (`HIVE_Q27_GDN_CHUNK`; own derivation: u = (I + A)⁻¹ W per 64-row chunk, see the kernel comment) and a
row-parallel conv. Lossy options (off by default, judged by the quality suite): `HIVE_Q27_PREFILL_QUANT=1` (W8A8 / W4A4 cuBLASLt, bf16
straight out of the GEMM), `HIVE_Q27_W4=1` (NVFP4 copies of the FP8 matrices: decode reads them, and with PREFILL_QUANT the prefill runs
W4A4 on them with a dynamic activation scale).

**Speculation.** `HIVE_Q27_DFLASH=<Qwen3.8-27B-DFlash2 dir>` replaces the MTP block with the DFlash2 block drafter (math after
z-lab/dflash, MIT, Copyright (c) 2026 Z Lab — own CUDA code, attribution in `q27_dflash.h`): target hidden of layers 5/19/33/47/61 is
captured in every forward and turned into the drafter's context K/V ring (2080 slots), one 8-row block per draft (7 drafts), candidate
selector on the top-16 of the (64K draft-vocabulary) head. `HIVE_Q27_DFLASH_FP8=1` stores the drafter in FP8 per row (drafts only).
Verify rollback replays the kept rows from one recurrent-state snapshot per sequence (no per-row snapshots). Batched drafts
(`mtp_draft_batch`) stack up to 16 sequences in one pass; verifies take up to 32 rows.

**Draft vocabulary** (`config/q27-draft-vocab-64k.bin`, 65,536 token ids, `tools/build_draft_vocab.py --size 65536 --include-script hangul
--balance`, Qwen3.8-27B tokenizer): token frequencies of ShareGPT_V3_unfiltered_cleaned_split.json (English) and ShareGPT_ko_dataset_2.json
(Korean), balanced between the two, plus every Hangul-script token; the draft heads score only these rows (verification uses the full head).

**Speculative method (measured per concurrency, 600 W, all exact verification).** q27_check (128 tokens, 2 prompts): DFlash2 3.1–3.6
tokens/round, 165–187 tok/s; DSpark (`HIVE_Q27_DFLASH=<Qwen3.8-27B-DSpark>`, auto-detected: 7-row block, full-context ring, YaRN rope,
Markov bigram bias, confidence head as the gate's confidence) 2.6–2.7, 137–144 tok/s; built-in MTP k=7 3.5, 146–151 tok/s. hived (per
request tok/s, c1 / c4 / c16): DFlash2 132 / 84 / 39.4 · DSpark 97.5 / 72 / 38 · MTP 101 / 61 / 37.5 · no speculation 68 / 62.5 / 38.3 —
DFlash2 for c ≤ 4; at c16 no method gains (the gate already falls back to plain steps). DSpark weights: `license: other`; its reference
code (SpecForge, partly adapted from DeepSpec MIT) was read for the math only.

**Quality gate (non-thinking quality_eval suites ruler / qa / code / tool, same seeds; ops skipped: it has thinking-on
streams).** Baseline twice: identical (noise floor 0): ruler 100 %, qa 90 % (ko 92.5, en 87.5), code 100 %, tool 95.5 %.
`HIVE_Q27_W4=1` (NVFP4 decode copies of the FP8 matrices, bf16 prefill): identical on every category, oracle top-1 9/9 → PASS (default
candidate). W4A4 prefill (+W4): qa.ko 87.5, ruler 94.3 → FAIL. W8A8/W4A4 prefill (`HIVE_Q27_PREFILL_QUANT=1`): qa.ko 90, ruler 97.1 →
FAIL. Both stay opt-in.

**Chunked GDN prefill fix (2026-10-10).** The chunk scan took log(decay gate); a gate that underflowed to 0 made −inf − (−inf) = NaN
in every later decay factor: NaN states, garbage decoding and an out-of-range read in the drafter's selector (hived died on tool prompts
and on one 32K ruler prompt). The log is floored at 1e-30 (contributes exp(−69), nothing); the selector also maps empty top-16 slots to
token 0.

**Serving.** KV grows on demand (×1.5, at most +8192 positions per step); a failed device allocation in the serving path asks hived to
evict the least recently used idle session (`set_kv_reclaim`, `trim_seq` frees its KV) and retries, otherwise the request fails (the
daemon stays up). Gate passed: 16 × 32K sessions, 2 × 64K, c16, 64K again. Session images copy device ↔ host through pinned staging.

| 600 W, q27_check | lossless | lossy (PREFILL_QUANT + W4) |
| --- | --: | --: |
| decode M=1 / M=8 / M=16 step | 14.4 / 18.5 / ~22 ms | 12.0 / – / 20.6 ms |
| DFlash2 k=7 spec (p3, 64 tok) | 192–229 tok/s, 3.8–4.6 tok/round | 182 tok/s (128 tok) |
| prefill 1K / 8K / 32K / 64K | 0.29 / 1.74 / 7.5 / – s | 0.13–0.21 / 0.79 / 3.67 / 9.11 s |

Not done: sleep levels, MTP/DFlash when the model does not fit whole, a fused-dequant bf16 prefill GEMM (the lossless prefill pays a
dequantization pass per matrix).

## VRAM budget and the KV tier

Under a VRAM budget (`HIVE_MODEL=27b HIVE_VRAM_GB=…` → `HIVE_VRAM_LIMIT_MB`, or `HIVE_Q27_VRAM_MB`) the engine plans its placement before
loading (`[q27] placement:` in the log). The 27B is dense, so what does not fit runs on the CPU — never a refusal.

**Placement.** Every matrix is counted as it will be stored on the device: the checkpoint bytes plus the cuBLASLt-tiled scale copies of
NVFP4 matrices and, with `HIVE_Q27_W4=1`, the NVFP4 decode copies of the FP8 matrices (6.3 GB + ~0.9 GB of tiled scales; counting the
checkpoint bytes only had placed all 64 layers in a 32 GB cap that then measured 33,330 MiB after the load). With a DFlash2 / DSpark drafter
and a draft vocabulary (`HIVE_Q27_DRAFT_VOCAB`), the drafter, its rings and its draft head are placed first (`HIVE_Q27_DRAFTER_FIRST`,
default on under a budget; `0` = the drafter only when every layer and the `lm_head` fit), so speculation stays on when layers run on the
CPU (their hidden rows are captured from the host stream). Then layers 0..N−1 in order, the `lm_head` (before the layers when layers must
go to the CPU: `HIVE_Q27_HEAD_FIRST`, measured at 16 GB c1 15.7 vs 15.0 tok/s), the rest on the CPU engine. The embedding table goes to VRAM
when it fits, otherwise the host table is mapped into the device address space for the device-side gathers (`HIVE_Q27_EMB_MAPPED`,
default on under a budget), so the drafter keeps its CUDA graphs. `HIVE_Q27_GPU_LAYERS=N` forces N layers (tests);
`HIVE_Q27_PLAN_ONLY=1` prints the plan and exits without a GPU.

**KV tier** (`HIVE_Q27_KV_TIER`, default on under a budget). Layers, `lm_head` and drafter are placed as if KV took no VRAM. KV buffers
live in VRAM while the leftover budget lasts (measured at the end of the load, `[q27] KV tier (measured)`), beyond it in pinned host memory
mapped into the device address space — the attention kernels read either through the same pointer with the same arithmetic, so the
values do not depend on the tier, and every context up to `--max-ctx` fits while short chats keep the all-GPU speed. At 32 GB the VRAM
budget holds ~100K positions of one sequence; the profile runs `--max-ctx 262144`.

- Before a KV buffer spills, the KV of idle pooled sessions goes first: hived's reclaim moves the least recently used idle session to a
  host image (a session being admitted is never chosen — see the fix below).
- Host-tier buffers grow in place (`HIVE_Q27_KV_HOST_GROW`, default on: the address range of the plan context is reserved and pages are
  registered as the cache grows). The previous growth allocated a new pinned buffer and copied the rows on every step: a 72.8K-token prompt
  made 67 pinned allocations (6.2 s at ~1.3 GB/s) and copied 5.6 GB host to host. When the VRAM KV budget is under 4 GiB, a background thread
  pins `HIVE_Q27_KV_HOST_PREPIN_MB` (4096) ahead of use in ranges of `HIVE_Q27_KV_HOST_SLOT_MB` (128); `HIVE_Q27_KV_HOST_POOL_MB` (8192)
  caps the pool of pinned ranges kept for reuse.
- A prefill chunk's attention reads a host-tier layer from a staging copy in VRAM (the kernel reads every key once per 64 query rows; over
  PCIe that would dominate). The copy of the next host-tier layer runs on its own stream while the layers in front of it compute
  (`HIVE_Q27_STAGE_PREFETCH`, default on). The staging buffer is taken within the KV budget, or beyond it while 256 MiB stay free; else
  idle sessions' VRAM KV is reclaimed, then passed layers of the same sequence move to the host tier. Without it the chunks read the host
  rows directly (measured at 32 GB: 88.9 s for one 8K-position stretch of a 32K prompt).
- W4 decode copies (`HIVE_Q27_W4=1`, `config/q27.env`) are dropped when keeping them would leave less than `HIVE_Q27_KV_TIER_MIN_MB` (4096)
  of VRAM for KV with every layer, the `lm_head` and the drafter on the GPU — speculation is worth ~2–3× at c1, the W4 copies ~10 %; decode
  then reads the checkpoint's FP8 matrices (the lossless path). `HIVE_Q27_W4_PARTIAL=1` (opt-in) keeps as many copies as fit after
  `HIVE_Q27_W4_KV_KEEP_MB` (1024) of KV and hands them back when KV runs out: at 32 GB c1 158.9 → 169.8 tok/s, but the KV budget fell to
  0.97 GB and 32K / 64K prompts went from 7.2 / 21 s to over 600 s, so it is off.
- The reserve under a budget adds the CUDA graphs, cuBLAS workspaces and drafter rings (768 MiB) and a load slack
  (`HIVE_Q27_LOAD_SLACK_MB`, 2048: the load allocated 3.0–3.8 GB more than the plan's estimates at 48 / 32 / 24 GB). Recurrent states are
  reserved for `HIVE_Q27_SESSIONS` sequences: default 2, 4 under a budget, 16 under the KV tier (every sequence of a full batch keeps its
  state in VRAM; only KV may spill). Prompt-checkpoint snapshot slots shrink to 512 MB under a budget (`HIVE_Q27_CKPT_SNAP_MB`, else 8192).
- `HIVE_Q27_KV_TIER=0` falls back to the KV plan (`HIVE_Q27_KV_PLAN`, default on): every GPU attention layer also reserves the KV of one
  sequence at the plan context, and the layers that do not fit with their KV run on the CPU (`HIVE_Q27_KV_PLAN=0` = neither).
- Diagnostics: `HIVE_Q27_KVLOG=1` (KV tier allocations and per-prompt KV costs), `HIVE_Q27_MEMLOG=1` (device bytes per load phase),
  `HIVE_Q27_KV_BUDGET_MB` (tests: cap the VRAM KV budget to force the host tier).

**Fix: repeated long prompt under a budget.** At 32 GB the same 34.8K-token prompt sent twice could crash the daemon: restoring the
session's image allocates KV, under VRAM pressure that allocation runs the KV reclaim, and the reclaim picked the session being restored
(its last use was still the previous request) — its sequence was trimmed under the load ("q27 image position mismatch", or a CUDA
invalid argument while staging). hived now marks a session as being admitted before its sequence is taken from the pool and keeps the
mark for the whole admission job, prefill included. The full benchmark at 32 GB is unchanged with the fix (c1 / c4 / c8 158.4 / 445.0 /
744.9 tok/s; 8K / 32K / 64K 1.00 / 4.66 / 11.76 s).

Measured by VRAM size (README table): 96 / 72 / 48 GB keep every layer, the drafter and the W4 copies on the GPU (c1 ~190 tok/s, 64K in
11.1 s); 32 GB keeps every layer and the drafter, drops the W4 copies and spills KV beyond ~100K positions: c1 158.8 tok/s, 64K in 11.8 s.

The batch gate does shrink k (c4 settles on 11–21 rows of 32, ≈ 1.8–4.3 drafts per stream instead of NInfer's fixed 7), because the per-row

### Service-path TTFT and arrival stalls (2026-10-10)

  for the first 16 requests and 163-168 ms from the 17th on: from then on every admission evicts the oldest idle session of the 16-session

### GDN prefill in WY form — accuracy gate (2026-10-11)

The first gate for the WY rewrite compared each variant's GDN states after the whole prompt against the row loop (all layers run on their own
outputs). Even an fp32 WY build (3 × TF32 products) scored state cos min 0.937 / mean 0.987 there, against the shipped chunk scan's 0.950 / 0.988,
and bf16 hi / lo splits did not move it — the metric mostly measures how 48 layers amplify upstream differences on a repetitive prompt (the
worst head is 0.55-0.8 for the shipped scan too), not the kernel. The gate is therefore per-layer local error: the row loop's layer inputs are
injected into every layer of every variant (q27_check `Q27_CHECK_INJECT`), and each GDN layer's state and outputs are compared with the injected
row loop's (`HIVE_Q27_GDN_DUMP`), on p681, a 2048-token piece of p6k, of p32k and of a 64K bench prompt — WY must be at or below the shipped
scan's local error — plus prefill-end logits at the shipped level and the quality-gate suites. A free-running decode comparison is not
used: on p6k a near-tie at the prefill end (margin 0.15-0.57 logits) flips the first token between equally valid forms and every later row then
compares different text (that looked like "top-1 0/17").

### Pressure test, 2026-10-11 (hived_q27, 96 GB, ctx 262144, 16 concurrent conversations)

16 conversations grew together by ~30K-token turns to 182K tokens (6 rounds), then four old conversations returned (211K), then cold re-runs
of four last turns on fresh sessions and a health check. 100 / 100 requests completed; cold re-runs equal to the warm answers (4 / 4, text

0; round walls 56 / 94 / 247 / 383 / 552 / 757 s, return turns ~60 s at 211K). hived RSS median 36 GiB, max 45 GiB; VRAM ≤ 97.2 GB.
